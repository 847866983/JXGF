## 1. 自动更新原理

更新链路分两段：

```
electron-builder（打包时）           electron-updater（应用运行时）
─────────────────────────           ─────────────────────────────
读取 electron-builder.yml 的         读取打包时写入应用的 app-update.yml
publish 段                            （其内容来自 publish 段）
   │                                     │
   ▼                                     ▼
生成 latest.yml（含版本、           checkForUpdates() 下载 latest.yml，
文件名、SHA512、下载地址）           与本机版本比对
   │                                     │
   ▼                                     ▼
连同 Setup exe 一起上传发布        有新版本 → 下载安装包 → 校验 SHA512
                                          → quitAndInstall() 退出并安装
```

关键点：

- **`latest.yml` 是更新的“信标”**：它记录了最新版本号、安装包文件名、文件大小与 SHA512 校验和、下载路径。electron-updater 先拉它，再决定要不要下载安装包。
- 应用内封装见 [src/main/core/updater.ts](../src/main/core/updater.ts)：`check()` / `download()` / `quitAndInstall()`，开发模式（未打包）自动禁用。
- 应用启动后 5 秒会静默调用一次 `check()`（见 [src/main/index.ts](../src/main/index.ts) 末尾），只有打包版本会真正发起请求。

## 2. 把占位 GitHub 换成你自己的仓库

当前 [electron-builder.yml](../electron-builder.yml) 的 publish 段是占位符：

```yaml
publish:
  provider: github
  owner: frameforge-studio   # 占位：改成你的 GitHub 用户名或组织名
  repo: frameforge           # 占位：改成你的仓库名
  releaseType: release
```

改成自己的仓库：

1. 编辑 [electron-builder.yml](../electron-builder.yml)，把 `owner` 改为你的 GitHub 用户名（或组织名），`repo` 改为你的仓库名，`releaseType` 保持 `release`（发布到正式 Release 而非预发布）。
2. 准备一个有写权限的 GitHub Token（`repo` 权限即可）：
   - GitHub → Settings → Developer settings → Personal access tokens → 生成新 Token；
   - 勾选 `repo` 权限。
3. 在打包机器上设置环境变量（`electron-builder` 发布时读取）：

   ```powershell
   # PowerShell（当前会话生效）
   $env:GH_TOKEN = "ghp_xxxxxxxxxxxxxxxx"
   ```

   或在“系统环境变量”里永久配置 `GH_TOKEN`。

4. 执行带发布的打包（见 [第 3 节](#3-发布流程)）。

> 注意：`GH_TOKEN` 不要提交进仓库或写进任何配置文件。CI 环境（如 GitHub Actions）应使用 Secrets 注入。

## 3. 发布流程

### 3.1 本地打包 + 发布到 GitHub Releases

```powershell
# 先递增版本号（见第 4 节），再执行：
pnpm package
```

`pnpm package` = `electron-vite build && electron-builder --win`，产物在 `release/`：

- `镜序工坊-Setup-<版本>.exe`
- `latest.yml`（配置了 publish 后自动生成）

**如果配置了 `GH_TOKEN` 且 publish 指向自己的仓库**，electron-builder 会尝试自动把产物上传为新的 GitHub Release；若不想依赖自动上传，也可以手动用 `gh` 发布：

```powershell
# 1) 只打包（不上传）
pnpm package

# 2) 用 GitHub CLI 创建 Release 并上传产物
$ver = "0.1.1"
gh release create "v$ver" `
  "release/镜序工坊-Setup-$ver.exe" `
  "release/latest.yml" `
  --repo 你的用户名/frameforge `
  --title "镜序工坊 v$ver" `
  --notes "本次更新说明……"
```

### 3.2 发布后客户端的行为

已安装的旧版本应用下次启动时会：

1. 下载 `latest.yml` 发现新版本；
2. 提示用户下载（`autoDownload: false`，由界面触发 `updateDownload`）；
3. 下载完成后提示重启安装（`quitAndInstall`）。

> 前提：`latest.yml` 与安装包必须放在**同一个 Release** 里，且 `latest.yml` 里记录的下载 URL 能公网访问（GitHub Release 默认满足）。

### 3.3 首次验证建议

先在自己机器上：安装旧版本 → 发布新版本 → 打开旧版本，确认「发现新版本 → 下载 → 重启安装 → 版本号更新」整条链路走通，再对外发版。

## 4. 版本号管理

- 版本号唯一来源是 [package.json](../package.json) 的 `version` 字段（当前为 `0.1.0`）。
- 每次发版前**递增 `version`**，否则 electron-updater 判断“无新版本”，不会推送更新。
- 建议遵循 SemVer（语义化版本）：
  - 修复 bug：`0.1.0 → 0.1.1`
  - 新增功能：`0.1.0 → 0.2.0`
  - 破坏性变更：`0.1.0 → 1.0.0`
- `electron-builder.yml` 的 `releaseType: release` 表示发布为正式 Release（与 GitHub 的 `draft` / `prerelease` 区分）。
- 应用内版本显示来自 `app.getVersion()`，它读取打包时注入的 `version`，与 package.json 保持一致即可。

## 5. dev-app-update.yml 的作用与内容

项目根目录的 [dev-app-update.yml](../dev-app-update.yml) 是 **electron-updater 在“未打包”运行态** 读取的更新配置，用来把更新检查指向本地/测试服务器，避免开发调试时误连生产发布渠道。

```yaml
provider: generic
url: http://127.0.0.1:8080/
channel: latest
updaterCacheDirName: frameforge-updater
```

做开发态验证：

1. 起一个本地静态服务，例如：
   ```powershell
   npx serve ./fake-update-server
   # 或：python -m http.server 8080
   ```
2. 把某次打包产物的 `latest.yml` 与 `Setup exe` 放进该目录；
3. 把 `dev-app-update.yml` 的 `url` 指向该服务。

**重要**：当前 [updater.ts](../src/main/core/updater.ts) 在未打包时会直接返回「开发模式未启用」，因此要真正用 dev-app-update.yml 走通验证，需要临时改动两处：

1. 放开 `check()` 开头的 `if (!app.isPackaged)` 保护；
2. 在 `check()` 内设置 `autoUpdater.forceDevUpdateConfig = true`，强制未打包运行时读取 dev-app-update.yml。

验证完记得还原这两处改动，避免误连开发服务器。

> 更贴近生产的验证方式：直接 `pnpm package:dir` 输出未打包目录，运行 `release/win-unpacked` 下的可执行文件——此时 `app.isPackaged` 为 true，走的是正式 publish 配置，不需要 dev-app-update.yml。

## 6. 改用自建服务器 / 对象存储（generic）

不用 GitHub 时，把 publish 段从 `github` 换成 `generic`，`url` 指向存放 `latest.yml` 与安装包的目录（HTTP/HTTPS 均可）。

### 6.1 electron-builder.yml 改动示例

```yaml
publish:
  provider: generic
  url: https://download.example.com/frameforge/win
```

### 6.2 发布步骤

1. 本地执行 `pnpm package`，得到 `release/` 下的 `Setup exe` 与 `latest.yml`；
2. 把 `release/` 里的 `latest.yml` 与 `Setup exe` 一起上传到服务器/对象存储的 `https://download.example.com/frameforge/win/` 目录（**两个文件必须在同一目录**）；
3. 确认 `latest.yml` 里的下载地址能被客户端公网访问；
4. 客户端启动后即从该 `url` 拉取 `latest.yml` 判断是否有更新。

### 6.3 用对象存储时的注意事项

- 对象存储需要开启**公网读**（或通过 CDN 回源），桶名/路径区分大小写；
- `generic` 方式不支持 electron-builder 自动上传，需自己上传两个文件（可用 `rclone` / `ossutil` / `aws s3 cp` 等）；
- `latest.yml` 中的 `url` 由 electron-builder 按 `publish.url` 生成，换目录需保持路径一致。

### 6.4 频道（channel）进阶用法

如需 beta / stable 双通道，可在 [electron-builder.yml](../electron-builder.yml) 中把 `channel` 设为 `latest`（默认），开发态通过 dev-app-update.yml 覆盖为其他频道。单通道场景无需改动。

## 7. 签名与 Windows SmartScreen

### 7.1 现象

未做代码签名的安装包/可执行文件，在用户机器上会触发 Windows **SmartScreen** 提示：

- “Windows 已保护你的电脑”（蓝色提示，需点“仍要运行”）；
- 或“未知发布者”黄色警告。

原因：Windows 对无签名、下载来源不明的 exe 默认拦截。这不影响功能，但会显著影响用户信任与转化。

### 7.2 缓解方式

1. **购买代码签名证书**（OV / EV）：
   - OV 证书：签名后 SmartScreen 提示会明显减少，但新证书初期仍可能显示“未知发布者”；
   - EV 证书：可即时建立信誉，SmartScreen 基本不拦。
2. 在 [electron-builder.yml](../electron-builder.yml) 的 `win` 段配置签名（electron-builder 会在打包时对 exe 签名）：

   ```yaml
   win:
     target:
       - target: nsis
         arch: [x64]
     # 示例：使用证书文件签名（实际参数以你的证书工具为准）
     signtoolOptions:
       certFile: path/to/cert.pfx
       certPassword: '%CERT_PASSWORD%'
   ```

   > 证书密码建议用环境变量注入，不要明文写进仓库。
3. **长期积累信誉**：同一证书持续签名多个版本，SmartScreen 的信誉系统会逐渐放行。
4. **签名 + 正规下载渠道**（HTTPS 官网 / GitHub Release）组合，效果最好。

### 7.3 未签名时的用户侧提示

给用户的安装说明里可补充：出现 SmartScreen 提示时，点击“更多信息 → 仍要运行”。这是未签名应用的正常现象，不是程序报错。

## 8. 本机打包环境注意事项（实测）

2026-11-13 在本机（无符号链接权限的普通用户会话）实测打包，遇到并解决了两个环境问题，记录下来供后续打包参考：

### 8.1 winCodeSign 解压报「Cannot create symbolic link」

- **现象**：`electron-builder --win` 在下载 winCodeSign-2.6.0.7z 后解压失败，报 `Cannot create symbolic link ... 客户端没有所需的权限`，并触发 Go 侧 `app-builder.exe process failed ERR_ELECTRON_BUILDER_CANNOT_EXECUTE`。
- **根因**：winCodeSign 压缩包内含 macOS 的 `.dylib` 符号链接；Windows 上创建符号链接需要「开发者模式」或管理员权限，本机两者都无。
- **两种解法**（任选其一）：
  1. **开启 Windows 开发者模式**（设置 → 隐私和安全性 → 开发者选项 → 开发人员模式），或直接以管理员身份运行打包命令 —— 这是正规解法，打包后 exe 会带上图标与版本信息。
  2. 在当前 `electron-builder.yml` 里临时加了 `win.signAndEditExecutable: false`（跳过 rcedit 元数据编辑，exe 使用默认 Electron 图标）。**这只是本机验证用的临时开关**，正式发布请开启开发者模式后删掉该行恢复。

### 8.2 已实测通过的打包结果

- 安装包：`release/镜序工坊-Setup-0.1.0.exe`（约 78 MB）
- 更新元数据：`release/latest.yml`（version / sha512 / size / releaseDate，electron-updater 正是读它）
- 块映射：`release/*.exe.blockmap`（增量更新用）
- `release/win-unpacked/镜序工坊.exe` 已启动冒烟测试通过（12 秒无崩溃、无 stderr 报错）

> 把渲染层依赖（react / react-dom / react-router-dom / zustand / lucide-react）放到 `devDependencies` 后，安装包体积明显下降——它们由 Vite 打进渲染层 bundle，不需要出现在运行时 `node_modules` 里。只有主进程运行时真正 require 的 `ws`、`electron-updater` 保留在 `dependencies`。
